# Methodology: Experience-aware staffing for Float

This document describes what the repository actually implements. It is intended as a technical walkthrough and interview reference, not a claim that the model was deployed inside Float.

## 1. Problem and hypothesis

Float's documented Smart Assign behaviour is used as the benchmark: role fit is grouped into fit tiers, then availability is considered. The project tests whether adding evidence from an employee's previous work can improve the ranking for a specific client and project brief.

The hypothesis is that two employees with similar role fit and capacity may not be equally suitable when one has worked with the client, on similar projects, or with the proposed teammates.

**Scope:** this repository builds an independent recommendation engine using data exported from Float. It does not modify or integrate with Float's proprietary Smart Assign UI or internal ranking service.

## 2. Data: a synthetic agency loaded into Float

The experiment creates a fictional agency, Kestrel & Co, with a seeded generator in `src/world.ts`. The default run creates a 54-person agency, fictional clients and projects, employee roles and skills, allocations, and time-off records. It generates approximately 18 months of historical staffing plus future open roles.

Historical staffing choices are generated by a documented synthetic process. That process considers role compatibility, client history, industry affinity, prior collaboration with the producer, skill overlap, current workload, and random noise. A proportion of assignments are deliberately allocated to the least-loaded eligible person instead. The generator retains the selected employee as hidden evaluation truth.

The generated agency is loaded into a Float Pro trial through the public API by `src/load.ts`. The data is then read back through the public API by `src/pull.ts` and saved as `out/float-export.json`. Downstream feature engineering and ranking use this export, not the generator's hidden truth. This makes the recommender operate on the fields available through Float.

**Important data qualification:** the agency, project history, and historical staffing decisions are synthetic. They are not Float customer data or independently observed real-world staffing outcomes.

## 3. Extract and normalise the Float data

`src/pull.ts` exports people, roles, departments, clients, projects and project teams, phases, tasks/allocations, time off, and time-off types. `src/data.ts` converts the raw API payload into typed people, project, allocation, and leave records, and builds lookup maps by person, project, and employee.

The separate dbt/DuckDB pipeline in `warehouse/` stages the raw export, creates intermediate staffing-decision and person-project-history models, and builds candidate signals in a mart. DuckDB is used locally as the warehouse implementation; the README describes it as standing in for BigQuery.

## 4. Define the prediction unit and labels

The prediction unit is **one staffing decision for one role on one project**.

In `src/engine.ts`, each allocation becomes a decision. Allocations assigned to role placeholders represent open roles and are excluded from historical model training. For a historical decision, the chosen employee is the label: the candidate whose person ID matches the employee recorded on that allocation.

For each historical decision, the feature builder reconstructs the candidate pool that could have been considered. If the historically selected employee is absent from that pool, the decision is skipped rather than silently counted as a miss. The skipped count is written to the backtest report.

The candidate pool excludes people who:
- had not yet joined by the role's start date;
- would leave before the role's end date;
- were already on the project team;
- did not have enough remaining capacity for the requested hours over the role window.

The candidate pool and features are reconstructed as of the decision date, rather than using the employee's current profile or later project history.

## 5. Engineer the seven candidate features

`src/features.ts` calculates seven numeric features for every candidate-decision pair:

| Feature | Implementation |
|---|---|
| `titleFit` | Exact title match scores 1. Otherwise, title tokens, seniority distance, Jaccard overlap, and character-trigram similarity produce a lexical role-fit score. This is a project-built approximation, not Float's proprietary semantic matching. |
| `availability` | Free capacity after overlapping allocations and time off, expressed as a fraction of the person's capacity and capped at 1. |
| `sameClient` | Log-transformed, recency-weighted count of the candidate's previous projects for the same client. |
| `tagOverlap` | Fraction of the current project's tags supported by the candidate's recency-weighted history of project tags. |
| `textSim` | Cosine similarity between the current brief's TF-IDF vector and a recency-weighted profile of the candidate's previous project notes and tags. Client-name tokens are removed. |
| `knowsTeam` | Fraction of the other named project teammates whom the candidate has worked with on a previous project. |
| `skillMatch` | Count of the candidate's skill tags that overlap the project's tags, capped at 3. |

Historical project contributions are decayed by `exp(-daysBetween(projectStart, decisionDate) / 365)`, so more recent work contributes more strongly.

The feature order is fixed in `FEATURES` in `src/features.ts`; `src/models.ts` uses that same order for model weights and explanations.

## 6. Build the two ranking approaches

### Baseline: Float-style title and availability

`baselineScore()` in `src/models.ts` approximates the documented behaviour. It assigns a role-fit tier (strong, related, weak) and then adds the title-fit value and availability. The tier dominates the score.

This is a transparent project-built proxy based on Float's published description. It is not a reproduction of Float's proprietary source code.

### Experience-aware ranker: conditional logistic regression

The second ranker uses all seven features. In `ExperienceModel.fit()`:

1. Calculate the mean and standard deviation of each feature across the training candidate rows.
2. Standardise each candidate's feature vector.
3. Calculate a linear score: the sum of each standardised feature multiplied by its learned coefficient.
4. Within each historical decision's candidate pool, apply softmax to convert candidate scores into probabilities that sum to one.
5. Compare the probability assigned to the historically chosen employee with the observed choice using negative log-likelihood.
6. Aggregate gradients across decisions and update the coefficients using gradient descent.
7. Apply L2 regularisation to discourage unnecessarily large coefficients.

The defaults in code are 600 epochs, learning rate 0.3, and L2 coefficient 0.01. The model learns coefficients from historical choices; they are not hand-set feature importance weights.

This is a conditional choice/ranking setup: the probability is conditional on the candidate pool for that particular staffing decision. It learns to reproduce historical selections, which are a proxy label. It does not directly optimise employee performance, project outcomes, or client value.

## 7. Train and evaluate with a time-based split

`src/backtest.ts` builds the historical decisions and candidate groups, then splits them by the staffing decision's project start date:

- **Training:** decisions before 1 February 2026.
- **Test:** decisions on or after 1 February 2026.

The experience model is fitted only on the training groups. Both the baseline and the trained model are evaluated on the held-out test groups.

Metrics:
- **Hit@1 / first-pick accuracy:** percentage of decisions where the historically chosen employee is ranked first.
- **Hit@3 / top-three accuracy:** percentage where the historically chosen employee appears in the first three.
- **MRR (mean reciprocal rank):** average of the reciprocal rank of the historically chosen employee.

The README reports 205 held-out decisions for the default 54-person run: the Float-style proxy achieved 68% Hit@3 and 32% Hit@1; the experience model achieved 71% Hit@3 and 37% Hit@1. These results are measured against the synthetic historical choices, not Float customer outcomes.

## 8. Compare against captured Float Smart Assign recommendations

Separately from the historical holdout, `data/smart-assign-capture.csv` stores the top-three suggestions captured manually from Float's application for 20 live open roles on 17 October 2026.

The backtest compares those captured lists with the baseline and experience-aware recommendations. The README reports that the known synthetic generator choice appeared in the top three for 15/20 captured Float Smart Assign lists and 16/20 experience-model lists.

This is **not** a comparison against real staffing ground truth: the evaluation target is the generator's hidden intended choice for each synthetic open role. Float's actual suggestions are real captured product outputs, but the target used to score them is synthetic. The baseline's first-pick agreement with Float is also reported separately.

## 9. Data validation and leakage controls

The dbt tests are intended to protect the feature dataset:

- `assert_chosen_person_in_pool.sql`: every historical selected employee must exist in that decision's candidate pool.
- `assert_no_feature_leakage.sql`: the latest historical project used for a candidate must start before the decision's as-of date.
- `assert_ts_sql_feature_parity.sql`: SQL and TypeScript candidate signals must agree row by row. The README reports parity across 16,663 candidate rows.
- The dbt project also declares model tests for keys and relationships.

These checks validate important properties of the pipeline. They do not establish that synthetic staffing choices are a valid proxy for real-world staffing quality.

### Known methodological caveat: TF-IDF corpus timing

The current `TextIndex` in `src/features.ts` calculates document frequencies from all projects in the export when it is constructed. Candidate history aggregation itself filters to projects that started before the decision date, but the TF-IDF inverse-document-frequency weights can therefore reflect projects that started later.

The SQL leakage test checks historical project usage, but does not test this corpus-level IDF timing. For a stricter temporal evaluation, fit the text vocabulary and IDF statistics using only documents available at each training/evaluation cutoff (or use a fold-specific index), then rerun the backtest and parity tests. Do not describe the current implementation as having fully eliminated every possible source of temporal leakage.

## 10. Recommendation serving and system boundary

`src/engine.ts` shares the candidate-building and ranking logic between the backtest and recommendation engine. It returns ranked recommendations, the title-and-availability baseline, candidate-pool size, and short explanations based on positive feature contributions.

`src/mcp.ts` exposes read-only MCP tools including `list_open_roles`, `recommend_people`, `recommend_for_brief`, and `refresh_from_float`. The model is an independent service over exported Float data. Float's public API does not expose its internal Smart Assign recommendations, so the 20 recommendations in the capture file were recorded from the application UI.

## 11. What the experiment establishes, and what it does not

**It establishes:**
- a working data extraction and feature-engineering pipeline over Float API data;
- an implemented conditional-logit candidate ranker and a title/availability comparison ranker;
- a reproducible historical holdout experiment on a synthetic agency;
- a separately recorded comparison with Float's live Smart Assign suggestions;
- dbt checks for candidate validity, selected-person inclusion, temporal history usage, and TypeScript/SQL feature parity.

**It does not establish:**
- improved staffing outcomes for actual Float customers;
- production deployment inside Float or integration with Float's proprietary Smart Assign;
- causal improvement in project delivery, employee utilisation, client satisfaction, or revenue;
- generalisation to real agencies without validation on real historical staffing decisions.

## Reproduce the experiment

See the setup section in [README.md](../README.md). In brief: generate the synthetic world, load it into a Float account, pull the account export, run the backtest, and run the warehouse build. The backtest writes a row-level report to `out/backtest.json` when run locally.
